# courier-contracts

The contract between the Rust Engine and the Python adapters. Nothing here is code that runs in production; both sides test themselves against these files.

| Path | Contents |
|---|---|
| `schemas/v1/` | JSON Schema (draft 2020-12) for the envelope and each message type |
| `fixtures/v1/valid/` | Messages every implementation must accept |
| `fixtures/v1/invalid/` | Messages every implementation must reject; `_expectations.json` states why |
| `fixtures/v1/produced/` | Messages generated by real producer code (the Rust Engine). Never edit by hand: the Engine test compares its output with these files byte for byte, and the tests here validate them against the schemas. Regenerate with `make update-contract-fixtures`, review the diff, commit. Regeneration is refused in CI |
| `topology.yaml` | RabbitMQ exchanges, queues, bindings and routing keys |
| `tests/` | Checks that schemas, fixtures and topology agree |

## Rules

- **Fixture names** are `<message type>.<case>.json`, for example `job.result.success.json`.
- **Versioning.** The major version is in the directory (`v1`), in the routing key (`job.track.v1.dummy`) and in `schema_version` (`1.x`). A minor version may only add optional fields. Consumers ignore unknown fields and reject an unknown major version.
- **Formats** (UUID, timestamp) are written as `pattern`, not `format`, so every validator enforces them. Timestamps are UTC with a `Z` suffix; UUIDs are lowercase.
- **Size.** A message is at most 256 KiB (`limits.max_message_bytes`), enforced by publishers and consumers in code.
- **Secrets** never appear in a message.

## Changing a contract

1. Edit the schema.
2. Add or update a valid fixture, and add an invalid fixture (with an entry in `_expectations.json`) for each new rule.
3. Run `make test-contracts`.
4. Update the Rust and Python types; their contract tests read the same fixtures.

```
uv sync
uv run pytest
```
